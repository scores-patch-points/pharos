## What each test requires (stated now)
- **I7 (new)**: SOURCE.json has a 40-hex sha and exactly the seven khora paths with sha256; the shipped tree holds none of the seven (no byte-identical file anywhere, nothing under `upstream/` but SOURCE.json); fetched bytes (read-only `gh api` by this test, at the pinned sha) hash to SOURCE.json for all seven; `THIRD-PARTY.md` names khora, MIT, the pinned sha and carries the licence grant and a copyright line. Door level, with a `gh` shim serving the real bytes: `--with-verify-source --apply` exits 0, makes exactly the seven api calls and nothing else, changes nothing outside the state dir; with one flipped byte, a missing file, an empty body, a gh failure, or no gh at all it exits non-zero; plan makes zero gh calls; a failed check is not reported satisfied by a later plan. Controls: a planted byte-identical copy in a COPY of the tree is caught by the tree check; a SOURCE.json with a wrong hash is caught by the fetch check.
- **D1 kill -9**: for every k from 1 to N (N = number of mutating fs calls of `install all --apply`, counted in a run with a counting preload) kill -9 the process at the k-th call, with that call's write cut to half. After each kill: no destination file (`AGENTS.md`, `pharos.json`, `holon.json`) is torn (it is the original bytes, absent as at the start, or the complete new bytes); `status` is `partial` or `not-installed` (or `installed` only when the tree equals the full install), never `drifted` or `journal-invalid`, and for `partial` it names each file as `original intact` or `new content in place`; `undo-door all` then exits 0 and the home and target trees are byte-identical to before; a second undo is a no-op; and a second `install all --apply` after the kill finishes, `verify all` exits 0, and undo is exact. Two scenarios: existing AGENTS.md with external state; bare target with the default in-target state.
- **D2 drift**: after apply, edit `pharos.json` (pharos-core) and the pharos block of AGENTS.md (agents-md); `undo-door` exits non-zero (1), reports the file as kept/drifted, the edited bytes are untouched, the journal and backups are still there, `status` says `drifted`, a second undo still exits 1; after the human restores the exact applied bytes, undo exits 0 and the tree equals the original. Edit outside the block: undo exits 0, removes only the block, the human's line stays (README).
- **D3 foreign state-dir contents**: seed `<state>/backups/x`, `<state>/runs/x`, `<state>/x`, `<state>/sub/x`, a file named like a sha256 in backups that the journal does not reference; apply all, undo all (both the default `.pharos` and `--state`): every seeded file is byte-identical afterwards, `backups/` and `runs/` still exist (they pre-existed), nothing the installer created remains; and with a state dir that did not exist the whole jail is identical to the start.
- **D4 forged journal**: on an applied install, each of: edit a field in a middle line, delete a middle line, swap two lines, append a forged intent (mkdir of an outside empty dir), swap in attacker backup bytes, plant a reverse command for a shimmed tool: `undo-door` exits 3, touches nothing (jail identical before and after the undo call, victim dir still there, no AGENTS.md change, zero `curl` calls), `status` says `journal-invalid`. Control: the untampered journal undoes with exit 0. Extended (beyond the bare A1 words, from CHANGES section 2): a forged entry with a RECOMPUTED valid chain naming a path outside the declared touches, or a reverse command with attacker argv, is refused too.
- **D5 no-follow**: a symlink planted at `AGENTS.md`, `pharos.json` or `holon.json` immediately before the k-th mutating call (for every k, absent and existing variants) never lets the installer write through it: the outside victim file is byte-identical afterwards, nothing outside the jail changes; a symlink at the journal path, a hard link from an outside file to AGENTS.md (an in-place write would change the other name), and a FIFO at AGENTS.md (must not hang) are refused or replaced, never written through.
- **D6 real-home targets**: with the account home stood in by a directory inside the jail (and, for plan and apply refused cases, the true account home under the sandbox write wall): target = the home, `.ssh`, `.aws`, `.gnupg` (and `.kube .docker .azure`, `/etc`, `/usr`) exit 3 on plan and apply, also with `--yes-real-home`, also when the allowed-root list is empty, also as `--state` and as `--khora-dir`, also through a symlink; nothing changes. Control: a project folder inside that home is accepted (exit 0, verified).
- **D7 lock**: six parallel `install all --apply` with a slow-op preload (so they truly overlap), four rounds: every exit is 0 or 1 with `LOCKED`, at least one exit 0, the journal audit is clean (every line parses, seq is 0..n contiguous, every `prev` equals sha256 of the previous line), exactly one AGENTS.md block, `verify all` exits 0, no lock file remains, undo is exact. While a slow run holds the lock the lock file exists and a second run waits or reports LOCKED without interleaving; a lock left by a kill -9 holder is taken over (README) and the next apply exits 0.
- **README**: every command line in a fenced block that mentions `<pharos>` or `<dir>` has both inside double quotes; the three Do-this commands run literally (parsed shell-style, `<pharos>` = this tree whose path contains a space, `<dir>` = a sandbox directory whose name contains a space): plan changes nothing, apply exits 0, verify exits 0 and the text printed after `verified:` is the order `--text` prints, equal to the order the README states; every status value `status` can print appears in the Repair section; the three exit codes in Rules for agents match behaviour (3 for a `..` target, 2 for a bad flag); `--help`, `-h` and `help` print on stdout, exit 0, and name detect, install --plan, --apply, verify, status, undo-door, doors; the doors table lists exactly the ids `doors` prints; no "safe word", no private names; `pharos.json` and `holon.json` hold no absolute path and no home path, and `lib` resolved against the target is the library file.
- **I8 (updated)**: the patch applies to a fresh clone of khora main; deletes exactly the seven files; changes elsewhere only README-class files and files that referenced a removed path, every one listed; `claude-code/hooks/hooks.json` is among them and after the patch no hook entry points at a removed file; a README names pharos and the door; the checker lists the remaining dangling references (advisory). Controls (all must FAIL on the named check): the strict seven-only patch (hooks.json untouched), six of seven, an unrelated edit, a hooks edit missing from the listing, no README, a patch that does not apply.
- **rig**: the free-port precondition of `a_rig.validate` is an assertion that picks a free port itself (the rig binds an extra ephemeral listener when every well-known port is busy).

## Predictions (so a miss is visible); confidence in brackets
- I7: tree/hash/licence checks PASS [85%]. Door-level verify-source with my shim PASS [55%]; the most likely failure is the exact `gh api` argv the door uses (my shim understands `repos/<r>/contents/<p>?ref=<sha>` with or without a raw Accept header) or the door running gh with `--jq` or a different endpoint.
