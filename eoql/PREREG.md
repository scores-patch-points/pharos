# Pre-registration: EOQL, a query-and-update language projected from the fold

Written 2026-11-13 BEFORE any EOQL code or spec exists in this folder. Stamped with `.sha256` and `.time`. Origin: the user said "develop EOQL as a type of database that can be projected from the fold similar to the SQL database, and make sure data can flow any way. EOQL should be a vastly more powerful language." Nothing here installs, publishes or changes any other ledger.

## What EOQL is today (read, 2026-11-13)
There is NO EOQL specification. What exists: (1) `holodeck/index.html:5914-5929` `eoqlParse`, a source-scope grammar `OP(arg)` with nesting and AND/OR/NOT, binding only SEG, EVA, REC, SYN, DEF; CON, NUL, SIG, INS return "could not bind operator". (2) `holodeck/vendor/bare-metal/public/data-chat.js` (about lines 1308-1372) `eoTrace`: a DESCRIPTIVE read of a query as operators (SEG scope, EVA filter, CON follow, SYN aggregate, REC group-by or transform, DEF frame/sort/window, NUL unbound observation); it never writes to a log. (3) the public repo EOedge: chat turns compile to nested operator expressions (`chat-compile.js`), execute against an event log (`chat-execute.js`), with a receipt of the expression and events scanned. (4) `EOQL_TRANSLATION_STANDARDS.md`: on-screen EOQL blocks. So EOQL is a seed grammar and a reading convention, not a database language. This work DEFINES it; the verb-to-operator reading above is the project's declared theory, not a finding. Cells stay earned: EOQL never types a cell; a write names a KIND, and the kind's declaration entry in the log supplies the cell (pharos SPEC), exactly as `weave` does.

## The claim (falsifiable, in parts)
EOQL is a language whose evaluation IS a fold of the pharos log (no stored state, no stored answers) such that:
- **C1 projection.** An EOQL "database" is computed from the log; delete everything derived and it is rebuilt identically.
- **C2 flow.** Data flows any way between: pharos log (per-writer JSONL), blocks store, the placed lazy store, SQLite (the pharos-sqlite projection and SQL dump text), CSV, JSON, EOT text, and EOQL statements themselves (a log can be written as an EOQL statement sequence and replayed). Lossless pairs round-trip with identical entry ids; lossy pairs name exactly what is lost and never lose it silently; foreign data enters as entries with provenance in `basis`.
- **C3 closure.** The result of an EOQL expression is a value EOQL can take as input (a fold state with its held sets), a stored view is the EXPRESSION as an addressable event (never its result), and a query result equals the fold of the entries it read.
- **C4 power.** EOQL contains the relational core (SELECT, WHERE, JOIN, GROUP, HAVING, ORDER, LIMIT, subquery, CTE, window) AND answers more of the project's real questions correctly in ONE expression than SQL over the same data, on questions SQL's table model does not hold natively: held values with survivor counts, causal (not clock) latest, as-of any log position, counterfactual re-fold, perceiver windows, ancestry with conflict awareness, incomplete-range awareness, and result provenance/cost as first-class output.
- **C5 operators as the query algebra (what it teaches about EO).** The nine verbs (NUL SIG INS SEG CON SYN DEF EVA REC) plus a small DECLARED set of frame arguments suffice to express read AND write. The count of extra primitives that had to be added is the finding: few supports operators-as-query-algebra; many weakens it.

## Words I will not use unless earned
"vastly more powerful" is not a measured quantity. The report may say "more powerful" only if P1 AND P2 below both clear their bars; it will print the numbers and never "vastly". If P2 does not WIN, the report says EOQL did not beat SQL on this question set.

## Materials and comparators
Data: the 10,244-entry Premiere replay (`ledgers/pharos-lazy/data/replay`, DATA.sha256) and the 764-entry Ellison trial log (`ledgers/ellison-statements/pharos`), plus synthetic logs with planted forks, retractions, late arrivals and 10^5-10^6 entries (generators from `ledgers/pharos-lazy/test`, read-only copies). Never `pharos/log`. Sources read through the frozen library (`ledgers/pharos-lazy/baseline/pharos.mjs`, sha256 e869302b...) and the pharos-lazy placed API (`API.md`) behind a source interface. Comparator for SQL: the pharos-sqlite projection (`ledgers/pharos-sqlite`) opened with node:sqlite, with its documented limits (for example `latest` uses entry clock time, not causal order) recorded as they are. Raw scan floor reported. Core code Node built-ins only; node:sqlite only in adapters and tests.

## Roles (separation is the point; each blind to the next)
- **QA, question author** (no EOQL spec, no builder code): writes at least 60 beyond-SQL questions in plain language drawn from the real problems (Premiere: who created id X, which lane wrote last, anything in flight at write; Ellison: what did he say and on what basis; act-tag/intelligence: what is held at an address and how many pasts survive), plus at least 200 SQL-core queries (join, group, having, subquery, CTE, window) over the pharos-sqlite schema; computes GROUND TRUTH by an independent forward fold written by QA, sealed (sha256 + .time) before anyone answers.
- **SQLA, SQL answerer** (sees the SQLite schema only) writes the best SQL for each question; may use recursive CTEs, JSON1, windows, several statements, and says when it needs application code.
- **EQA, EOQL answerer** (sees SPEC.md only, not the builder code) writes the EOQL for each question.
- **B, builder** (sees PREREG, SPEC.md, the sources; never the sealed questions or ground truth).
- **T, test author** (not B): flow, closure, safety, fuzz and mutation harness.

## Tests and bars (bars are mine, fixed now, none external)
- **P1 SQL-core containment.** Every one of the QA SQL-core queries is run through the SQL-to-EOQL translator, executed, and compared with SQL's result (set equality; order-sensitive where SQL orders). PASS: at least 95 percent identical; every untranslatable construct is listed as a named gap in the report.
- **P2 beyond-SQL.** For each QA question, SQLA's and EQA's answers are executed and scored against sealed ground truth as correct in ONE statement, correct in several statements or with application code, or wrong. Primary measure: share correct in one statement, EOQL vs SQL, paired exact (McNemar) test. WIN if EOQL is higher by at least 20 percentage points with p below 0.01 and SQL is not above EOQL on P1 by more than 5 points; TIE if the difference is under 5 points; otherwise LOSE (per question class too: held sets, causal latest, as-of, counterfactual, perceiver, ancestry, incomplete-range, provenance). Also reported: expression length, count of statements, and wrong-answer rate (a wrong answer is worse than "cannot express").
- **P3 where SQL should win.** Large tabular scans and joins over the flat projection: time and bytes, EOQL vs SQLite; a LOSE here is expected for scans and is reported, not hidden. (Timings on a loaded machine are provisional; bytes and records touched are the stable measure.)
- **F1 flow matrix.** All declared ordered pairs among {pharos JSONL, blocks, placed lazy, SQLite projection, SQL dump, CSV, JSON, EOT text, EOQL statement sequence}: A to B to A returns the identical set of entry ids for every lossless pair; for lossy pairs the loss manifest equals the true loss (diffed by QA's independent comparator); foreign CSV/SQL/JSON enters with `basis` naming the importer and its input hash; 0 silent drops over at least 20 seeded inputs per pair.
- **F2 write path.** Executing EOQL write statements on an empty pharos yields entries whose ids equal those from direct `weave` with the same fields; no statement edits or deletes (deletion is a retraction entry); read-only is the default and writing needs an explicit mode; a SQL write into the projection becomes an appended entry and the database remains rebuildable (or the report states that SQL write-through was not built).
- **C1-C3 tests.** Delete-and-rebuild identity; view-of-a-view equals the inlined expression; a changed log changes the view's result without re-weaving; result equals the fold of the entries it read (100 percent over at least 1,000 random expressions); the stored view contains the expression and no answer.
- **R cost.** Each result reports entries read, bytes read and plan; address-scoped expressions on a 10^6-entry log read at most 2 percent of the log (the pharos-lazy W3 bar, reused); a cost budget aborts a runaway expression with a typed error.
- **E explain.** Re-executing a result's explain entry set gives the same result; held, determined and incomplete markers equal the forward fold's on 100 percent of QA's held-set and gap questions.
- **S safety.** Parser fuzz of at least 100,000 inputs: no crash, no hang beyond the budget, no write in read mode; injection strings in values cannot become statements.
- **T teaches.** Report (a) number of extra primitives beyond the nine verbs needed to answer all QA questions and to express all writes, listed by name; (b) the share of addresses whose answer changes between a full-knowledge and a perceiver-window reading (the replay's earlier figure was 52 of 247, to be re-measured); (c) whether any question needed a verb used in a way that contradicts the declared reading (listed).

## Mutants (each MUST be caught by at least one test)
M1 latest by entry clock instead of causal order; M2 collapse the held set at read without saying so; M3 ignore retractions; M4 ignore as-of; M5 perceiver window leaks ancestry from hidden writers; M6 view stores the answer, not the expression; M7 export drops a field without listing it; M8 import without `basis`; M9 write mode on by default; M10 cost budget not enforced; M11 SQL translator drops a HAVING; M12 result provenance lists entries not actually read; M13 counterfactual mutates the log; M14 parser executes a statement found inside a string value.

## Process
SPEC.md is written by the builder-side designer first and stamped before QA or EQA see anything but the spec; QA seals questions and ground truth before SQLA or EQA answer; builder never sees sealed material; fix loop at most 2 rounds with the reason for each fix logged and no test file edited by B; every post hoc ruling is written to RULINGS.md and does not change the raw result; reviewers (fairness of the power comparison, lossless flow, semantics against the wave fold and EO honesty) after the mutation run. Failures are reported as failures.

## What a pass would and would not show
A pass shows EOQL is sound as a fold-projected language and answers more of THESE questions in one expression than SQL over THIS projection. It does not show the same on other data, that users prefer it, that it is faster, that the nine verbs are the right algebra for every domain, or anything about the cells (earned, not typed here).
