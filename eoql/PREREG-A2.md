## Part A: 27 positions (declared theory, nothing earned)
- **A-1 Holding a position.** EOQL must be able to write, read, filter, group and carry every one of the 27 cell ids in `cells.json` as data. The `declare` statement therefore takes a cell literal as a PASS-THROUGH of what the writer says, exactly as pharos `weave` and the `kind` entry (`body = {name, cell}`) do. This resolves SPEC.md's open question 1 in favour of a literal, and it is consistent with PREREG's rule: EOQL never infers or defaults a cell, never validates that a label is correct, and every result that carries a cell marks it `cell_basis: declared-by-writer`. Labels are writer-typed and unchecked today (the main session measured this); EOQL says so on every result.
- **A-2 Position behaviour (declared, to be tested for sensitivity, not for truth).** Grain is the LAYER of the log a verb operates on: Ground = declarations and frames (kind, schema, holon, frame, priors), Figure = instances, Pattern = what a loop writes back (views, outputs, holon-declared patterns). SPEC-A2.md must state, for every operator at every grain, what the verb does at that position, so that two positions differ in behaviour and not only in label. This is the project's declared reading (pharos holon contract; schema-as-ground), not a finding.
- **A-3 The cube view.** A result form that returns a 9 by 3 grid of counts (operator by grain), and a filter by cell, by operator, or by grain.
- **A-4 Real versus synthetic coverage.** The main session found the real logs use 11 of 27 cells (Ellison 6, Premiere replay 10; no Pattern-grain and no SIG entry). The report states real coverage as 11 of 27 and labels evidence for the other 16 positions synthetic.

## Part A tests (independent author K; blind to the builder's code)
- **K1 representability.** For each of the 27 cells, a synthetic log with at least 3 entries per cell (including held forks and a retraction at each grain) is written through EOQL write statements, read back by cell, by operator and by grain; entry ids equal those from direct weave; 27 of 27 PASS or the failing positions are listed.
- **K2 flow of all 27.** The same synthetic log through every F1 pair in both directions: identical id sets and cell fields; a format that drops or merges a grain (for example CSV) must name it in the loss manifest. 
- **K3 position sensitivity.** For each of the 27 positions a constructed question whose EOQL answer differs when the same expression is evaluated at an adjacent grain of the same operator, and when the label of one entry is swapped; EOQL's answer changes in each case. A position whose answer does not change is reported as decorative (the finding, not a failure to hide).
- **K4 labels never inferred.** No result changes when a kind's NAME changes but its declared cell does not; every result with a cell carries `cell_basis`; a statement with an unknown cell id is a typed error and not a silent default.
- **K5 cube view equals an independent count** of the log by cell (K's own counter) on the synthetic log and on both real logs.
Mutants (each MUST be caught): KM1 drop grain and keep operator only; KM2 normalize an unknown cell to a default silently; KM3 cube view merges grains; KM4 infer the cell from the kind name; KM5 reject SIG or Pattern cells; KM6 a converter drops the grain field; KM7 a result omits `cell_basis`.

## Part B: repairs to P2 (exploratory, after seeing partial results)
- **B-1 Score the right file.** The P2 harness scores answers/eoql-A1.json (sealed after SPEC-A1); both files are scored and printed separately, labelled round 1 and A1. T's repair is logged in test/TEST-AMENDMENTS.md and touches only the P2 scoring files.
- **B-2 A fold-free SQL arm.** A new blind SQL answerer (SQLRAW) answers the same beyond-SQL questions with SQL over a PLAIN `entries` table (the log's own fields as stored: id, cell, kind, addr, body, of, seen, by, at; no precomputed pos, heads, conflicts, retracted or latest_causal), so SQL must carry the fold itself. This is SQL as a general database over the log as data. Both SQL arms (projection and raw) are scored against the same sealed truth.
- **B-3 Cost of an answer, beyond statement count.** For every answer, in EOQL and in each SQL arm: expression length in tokens, nesting depth, number of CTEs, and a yes or no on "re-implements the fold inside the query" (recomputes causal order, retraction waves or held sets by hand), judged by a reader who sees the answer and the definition only. The reviewers recompute a sample.
- **B-4 Decision rules for Part B.** Neutral, per question class, with the original P2 rule untouched: WIN for EOQL on B-2 if EOQL is correct on at least 20 points more questions than SQLRAW at p below 0.01 (McNemar); TIE under 5 points; else LOSE. The report may say "more powerful" only under PREREG's original wording rule; a B-2 win alone does not unlock it. The report prints the original P2, the A1 P2, and B-2 side by side, with their different standing (the original stamped; B added after seeing partial results).
