## What exists (read 2026-11-13, public repo eo-activibase (an earlier public repository by the same author); commit and file hashes in `prior/eo-activibase/SOURCE.txt` and `prior/PINS.sha256`)
EOQL v1, December 2025, about 7,400 lines: `foundation/eo_query_language.js` (the language: nine primitive operators, named compositions called holons, an expression language, a fluent builder, an AST), `eo_query_parser.js` (SQL text to EOQL AST), `eo_query_compiler.js` (EOQL AST to SQL for PostgreSQL, MySQL, SQLite, SQL Server and Oracle; MongoDB and Pandas listed as future), `eo_query_crosswalk.js` (a bidirectional dictionary between EOQL, SQL and relational algebra, user-extensible), `demo/eo_query_builder_ui.js`, `demo/eo_eoql_testing.js`, `test/test_eoql.js` (772 lines, about 55 tests: build, compile, parse, round-trip, crosswalk, edge cases). Its stated idea: EOQL is a universal query representation that can be written directly, parsed from SQL, and compiled to other languages.

## The operator-set discrepancy (declared, not decided by evidence)
v1 uses NUL, DES (designate), INS, SEG, CON, ALT (alternate), SYN, SUP (superpose), REC (recurse). The current canon (khora, EO-DB README, holodeck) is NUL, SIG, INS, SEG, CON, SYN, DEF, EVA, REC, with REC meaning recontextualize. SPEC.md and PREREG.md use the canonical set. Choice, mine and reversible by the user: EOQL v2 stays on the canonical set; v1 is its ancestor, a conformance corpus and a crosswalk source. The v1-to-v2 crosswalk is DECLARED theory: v1's SELECT/projection (DES), ORDER BY/CASE (ALT), windows/CTEs/subqueries (SUP) and WITH RECURSIVE (REC as recursion) have no verb of the same name in v2; where each job lands (for example transitive CON for recursion, DEF for ordering and framing) is written in SPEC-A1.md, and every job that needs an extra primitive adds to the T count of PREREG.

## New tests (independent author; fixed now)
- **V1 v1-conformance.** Every parse, compile and round-trip case in v1's `test/test_eoql.js` (the SQL strings and the schema they imply) is run through the v2 translator and evaluated on a fixture SQLite database built by the test author from those cases' implied tables; the rows equal those of the original SQL. PASS at 95 percent of executable cases; failures are listed by construct.
- **V2 compile-back.** For the QA SQL-core set (PREREG P1), SQL to EOQL v2 to SQLite SQL executes with the same rows as the original. For each beyond-SQL question the compiler either produces SQL that returns the same answer or reports a typed reason it cannot (held sets, causal order, perceiver windows, as-of): the count of questions that do NOT compile back is evidence for C4, reported next to P2.
- **V3 dialects.** For the v1 compile cases, v2's PostgreSQL, MySQL, SQL Server and Oracle text is compared with the text v1's own compiler produces, recorded by running the v1 modules ONLY under `node --permission` with read-only access to `prior/eo-activibase`, no network and no child process; differences are listed and ruled on, not hidden. Only SQLite is executable here; the other dialects are text-equivalence only, reported as such.
- **V4 untested targets.** MongoDB and Pandas are not installed on this machine (no mongod, no pandas); no claim is made about them unless an engine appears.
- **V5 what v2 adds.** A table of v1 holons and v1 test constructs versus v2, naming what v1 could not say about logs (as-of, held values, ancestry, perceiver windows, incomplete ranges, provenance, cost).
"Data can flow any way" now means two flows, both tested: data (PREREG F1/F2, formats) and queries (EOQL to and from SQL and the SQL dialects, V1-V3).
